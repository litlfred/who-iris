Phase 3 — Requirements definition (detail)

Skill crdm-requirements-template: Guide and template for CRDM Phase 3 — Requirements Definition. Helps the agent structure requirements from conversation using a REQ-### format with acceptance criteria, priority, and traceability.

Named by: CRDM close-out, CRDM data model, CRDM Phase 6 — implement, MVP, acceptance, CRDM Phase 1 — needs, CRDM Phases 2–4 — BPA and requirements, CRDM requirements, CRDM Phase 5 — beans and sign-off, SWOT situation analysis, Options analysis, Requirements filing: promote, organise, trace, supersede, or retire, Guideline Updates

This skill expands the Phase 3 summary in crdm-requirements-workflow.md and applies the crdm methodology.

Requirement format

One definition, shared with spec-kit: a statement, a conformance level, a source, at least one success criterion with its verification method, and a sign-off owner — the requirement-definition skill (skill_fetch requirement-definition) in the content layer. The fields below are CRDM’s rendering of it; Acceptance criteria are the success criteria. A requirement with none is not ready to post.

Each requirement has:

Field Format Example
ID REQ-### REQ-001
Title Short phrase “Beans filtered by epic type”
Description Plain language, no jargon “The agent can filter work items by their type (epic, story, task)”
Conformance SHALL / SHOULD / MAY / SHALL NOT (RFC 2119 / RFC 8174) SHALL
Acceptance criteria (= success criteria, ≥ 1) Testable, measurable, each with a key and a verification method (test / inspection / review / analysis) “SC-1 (test) — Given an epic with 3 child stories, when filtered by epic, then all 3 appear”
Sign-off owner Who says it is met — a named person or role “The BA”
Priority Must-have (High) / Should-have (Medium) / Nice-to-have (Low) Must-have (High)
Source Phase 1 needs statement / Phase 2 process activity ref “Needs statement §2 — BA cannot see work grouped by release”
Impact Phase 4 footprint “Schema: new type field on bean. Pipeline: none”
Estimated scope Work item count / PR sizing “2 beans, 1 PR”

Priority scale and conformance keywords

CRDM separates implementation priority (how essential a requirement is when sequencing work or trading off scope) from normative conformance (how strictly an implementation must behave once it claims conformance to that requirement):

1. Priority scale (High / Medium / Low = Must-have / Should-have / Nice-to-have)

Aligned with PHII’s Defining and Validating System Requirements Guide (library/phii-2021-defining-and-validating-requirements-guide, p. 2) and PATH & PHII (2012) (library/path-2012-common-requirements-mhis-crdm, p. 1):

Priority label PHII / PATH CRDM scale Meaning
Must-have (Must) High Essential to the core business process; the system cannot satisfy the process goal without this capability.
Should-have (Should) Medium Important for operational efficiency or completeness; expected in standard operation, though a temporary workaround may exist.
Nice-to-have (Nice-to-have) Low Desirable enhancement that improves convenience or secondary workflows when resources permit.

2. Normative conformance keywords (SHALL / SHOULD / MAY / SHALL NOT)

While PHII’s informal prose grammar phrases requirement statements as “The system must or should…” (phii-2021-defining-and-validating-requirements-guide, p. 1), the separate Conformance field uses uppercase normative keywords governed by IETF BCP 14 — library/rfc2119-key-words-requirement-levels (RFC 2119) and library/rfc8174-uppercase-vs-lowercase-2119-key-words (RFC 8174, specifying that only UPPERCASE words carry RFC 2119 normative meaning):

  • SHALL (MUST) — mandatory requirement of the specification
  • SHOULD (RECOMMENDED) — recommended; valid reasons may exist in particular circumstances to ignore, but full implications must be understood and weighed
  • MAY (OPTIONAL) — truly optional capability
  • SHALL NOT (MUST NOT) — absolute prohibition

Generating from conversation

4-step elicitation

  1. Listen and deconstruct — identify the nouns (entities), verbs (capabilities), and adjectives (qualities) in the BA’s description
  2. Disentangle what from how — “I need to see beans grouped by release” is a requirement; “use a Jekyll page” is an implementation choice
  3. Formulate testable criteria — every requirement must have a Given/When/Then or a checkable statement
  4. Validate with the BA — read it back. “Does this capture what you need? Anything missing?”

The document is a requirement set

The requirements document as a whole is a RequirementSet (bootstrap-tools/schemas/requirement-set.ts, published as bootstrap/schemas/requirement-set.schema.json): reqset:<slug>, the methodology, the issue, a stage — draft → proposed → approved → planned → in-progress → delivered → accepted, or rejected, cancelled, superseded — its members (req: references, each with its own decision), its work plan (work item ids) and its sign-offs. Commit it beside the proposal as <slug>.requirement-set.json, or as a requirementSet: key in the proposal’s front matter; check:requirements judges it.

The set’s stage and each member’s status are independent — a requirement outlives the document that proposed it — with one link enforced: a set is accepted only when every member it approved is in-force. The stage moves only through a sign-off (Phase 5’s BA_Signoff, close-out’s BA_Confirm), and check:requirements refuses approved/accepted without a human sign-off, planned without work items, and cancelled without a reason.

- [ ] **REQ-001** (SHALL) — Beans filtered by epic type

  - _Acceptance:_ `SC-1` (test) — Given an epic, when `beans list --type epic`, then only epics appear
  - _Sign-off owner:_ the BA

Traceability

Every requirement traces in both directions:

Needs statement (Phase 1)
    ↓ "Source" field
Requirement (Phase 3)
    ↓ "Impact" field
Impact assessment (Phase 4)
    ↓ bean reference
Bean (Phase 5) — names its REQ / req: statements; `## Done when` copied from their acceptance criteria
    ↓ PR link
PR (Phase 6)
